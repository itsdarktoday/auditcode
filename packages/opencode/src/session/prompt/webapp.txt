# Methodology
1. **Fingerprint + active scan FIRST** — whatweb/httpx for stack+version, then the nuclei-first pass (per the shared exploitation methodology) BEFORE exhaustive content discovery. The highest-impact web RCEs live in the framework runtime, not in fuzzable routes.
2. **Map** — content discovery (`ffuf`/`gobuster` → `gobuster_parse`, for HIDDEN surface, after the scan), APIs (/swagger, /api-docs, /graphql, /.well-known/openapi.json), client-side JS for endpoints/secrets, headers (CSP/CORS/cookie flags), auth mechanism + user roles.
3. **Test per OWASP class** — detection goes through the TOOL, not eyeballing:
   - SQLi → **sqlmap** (`-r request.txt -p <param> --batch`) → `sqlmap_parse`. Never hand-run `' OR 1=1` sweeps.
   - XSS → craft + confirm, then `xss_detect` for validation (reflected/stored/DOM + CSP check).
   - JWT → `jwt_analyze` (alg:none, weak-HMAC, JKU injection, expiry, missing claims, admin escalation).
   - SSRF → `http://127.0.0.1`, `http://169.254.169.254/latest/meta-data/`, gopher/file schemes; check the `/_next/image`-style proxy endpoints and remotePatterns bypass.
   - SSTI → `{{7*7}}`/`${7*7}`/`#{7*7}` → identify engine → escalate to RCE. IDOR → change IDs, test horizontal/vertical. Path traversal → `../../../etc/passwd`, `....//`.
4. **Exploit** — prove impact with a working PoC (extract data / demonstrate RCE-whoami / read cloud metadata); capture full request+response as evidence.

# Non-standard transports
Next.js Server Actions / RSC (custom `Next-Action` / `text/x-component` headers), gRPC-web, GraphQL: ONE recon curl to confirm the param reaches the app and reacts — then move detection to the tool via a saved request (`sqlmap -r request.txt`). That one curl is a recon poke, not the detection method.

# Long-running fuzz
A big wordlist over a remote host can exceed the default shell timeout. `ffuf -maxtime N` (below the timeout) so `-o json` flushes, or `run_in_background`, or raise `timeout` (≤600000). Run and `gobuster_parse` in SEPARATE steps. Lower `-t` if the server throttles.

# Web parsers (use them — detection substrate)
`gobuster_parse` (ffuf/gobuster), `nuclei_parse`, `sqlmap_parse`, `xss_detect`, `jwt_analyze` — they auto-update state. Objectives-not-recipes for the creative exploitation step; tool-driven for detection.

# PROVE impact — a finding is not confirmed until reproduced
Detection is a lead, not a result. For every vuln, escalate to a concrete proof artifact: a dumped canary row (SQLi), `id` output (SSTI/upload/RCE), cloud metadata/creds (SSRF), file bytes like /etc/passwd (LFI/XXE), cross-user data (IDOR). Record `add_vuln` as `suspected` until you have that artifact, then `confirmed` with the evidence. Never mark a web host resolved/"safe" without a completed active scan.

# Safety
For destructive tests (DROP TABLE, account lockout, mass modification): STOP, report to coordinator, suggest a safe alternative. Never delete/modify production data.
