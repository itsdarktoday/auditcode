## 1. Contribution Summary

Finite Monkey Engine is a self-described "Security analysis pipeline for code auditing: **Planning → Reasoning → Validation**" (README.md) built as a three-stage, database-persisted LLM audit engine. Its distinctive contribution is not a novel static analyzer but a complete *validation methodology*: Planning converts a codebase into scannable units by having Codex extract "business flow groups (Gi) / business flows (Fi)" from a tree-sitter function catalog and then materializing a Cartesian product of "Fi × checklist rule_key" into `project_task` rows; Reasoning re-scans each flow with a deliberately *neutral, checklist-driven* prompt that allows 0..N high-confidence vulnerabilities in a fixed JSON schema, split idempotently into one row per vulnerability (`project_finding`); Validation then re-checks every single finding with an isolated, read-only Codex agent that must perform multi-step search-and-cross-reference before emitting a verdict from a fixed eight-value taxonomy, with full evidence objects and a machine-readable audit record.

The engine is unusually explicit about its anti-hallucination evolution: v1 relied on induced hallucination ("这个代码里面有一个漏洞，请你把它找出来" — philosophy_of_monkey.md), while the v3 `forward` branch documents removing "诱导式上下文（例如'已确认存在漏洞/只有一个漏洞'）" (forward_diff_and_ddl.md) in favor of neutral prompts, an empty-array escape hatch, evidence requirements, and conservative verdicts. Its most reusable assets are: (a) the taint-model × question-direction methodology (six abstraction levels of taint templates crossed with forward/reverse LLM questioning), (b) the structured finding-level verdict taxonomy with explicit false-positive elimination criteria, (c) the sandboxed agentic judge with mandatory evidence retrieval, (d) the task/finding data-model separation enabling idempotent re-runs, and (e) hard-coded context gates (design docs, explicit invariants, coverage thresholds) injected into prompts.

## 2. The Most Valuable Techniques / Gates Worth Preserving
### 2.1 Taint model × question direction as orthogonal axes
`Methdology_approach.md` formalizes the core finding gate as a taint path: "有没有一条路径，把「不可信 / 不受控的东西」传递到「敏感 / 危险的地方」，并且这条路径中间**缺少足够的约束或净化**？" — a Source → Sink path without a sufficient Sanitizer. Crucially it separates *what to look for* from *how to ask*: "「要找什么」（污点模型）和「怎么问」（正/反向）是两条互不混淆的轴，扫描方法 = 污点模板 × 提问策略。"

### 2.2 Six abstraction levels of taint templates
The methodology defines six reusable finding templates, each with Source/Sink/Sanitizer examples: **Invariant** (data-layer equalities like `totalSupply = Σ balances`), **Assumption** (business-layer preconditions like "users must deposit before borrowing"), **Hypo/Expression** (line-level anchors such as `externalContract.call{value: amount}("")`), **Temporal** (state-machine transitions, "能否在不该进入某状态时强行进入？能否跳过必要阶段？"), **Composition** ("A 和 B 各自安全，但 A→B 或在 C 条件下同时执行 A+B 会出问题吗？"), and **Boundary** (overflow/underflow, array bounds, gas exhaustion). This is a ready-made checklist ontology for any audit agent.

### 2.3 Forward (interrogative) vs Reverse (assertive) prompting
Forward framing ("假设**可能**有问题，也可能没问题；你帮我从头到尾检查一下") allows the model to say "no problem" but must give reasons; Reverse framing forces path construction: "我们**已经知道**这里存在符合某个模板的漏洞；你的任务是：找到具体是哪里，怎么利用，影响多大" and "不允许\"轻易宣称没问题\"，必须努力去构造一条满足模板的路径." The recommended workflow is a two-loop hybrid: forward-screen with Hypo templates, then reverse-assault with Assumption/Invariant/Temporal templates.

### 2.4 Neutral reasoning prompt with empty-array escape hatch (anti-induction gate)
`src/prompt_factory/vul_reasoning_json_prompt.py` is the engine's central false-positive gate: "Be neutral: vulnerabilities may or may not exist." plus "Only report vulnerabilities that are **high confidence** and would cause real harm. / Do NOT report intended design, best-practice suggestions, or hypothetical risks without exploitability. / Evidence MUST come from the provided code (include file/line range and a short excerpt)." The schema `{"schema_version":"1.0","vulnerabilities":[{"description":"string"}]}` permits "It MAY be an empty array [] if no high-confidence vulnerabilities exist", with descriptions constrained to "around 100-200 English words" and a cap of 5 most-harmful items ("Do NOT stop after the first vulnerability"). `forward_diff_and_ddl.md` records why: the legacy prompt contained "诱导式上下文（例如'已确认存在漏洞/只有一个漏洞'）" which inflated false positives.

### 2.5 JSON-only output discipline
`PeripheryPrompt.guidelines_json_only()` appends eleven hard constraints to the reasoning prompt, among them: "Assume atomic execution (no cross-transaction interruption/manipulation) and positive numbers unless code shows otherwise.", "Do NOT say \"attacker uses some way\"; provide concrete, reproducible steps and parameters.", and "Assume attacker is NOT the contract owner and has no privileged admin roles unless the code explicitly allows it." These are cheap, verbatim-reusable de-escalation gates that eliminate the most common LLM audit noise (privileged-role claims, fantasy interleavings, hand-wavy exploits).
### 2.6 Impact allowlist gate
`PeripheryPrompt.impact_list()` requires every reported vulnerability to satisfy at least one of ten concrete harm classes — e.g. "a. Manipulation of governance voting results. / b. Direct theft of any user funds, at-rest or in-motion… / e. Protocol insolvency. / i. Griefing (an attacker causing damage to the users or the protocol without any profit motive)". This converts vague "risk" claims into a checkable impact taxonomy.

### 2.7 Hard-coded false-positive elimination heuristics (legacy validator)
The earlier multi-round validator (`src/prompt_factory/vul_check_prompt.py`, `vul_check_prompt_claude_no_overflow_final`) encodes blunt but effective project-specific gates: "1. If the vulnerability is an integer overflow vulnerability, directly conclude that the vulnerability [does not exist]" (Solidity ≥0.8.0), "2. If the vulnerability is a reentrancy vulnerability, directly conclude that the vulnerability [does not exist]", "3. If the vulnerability is a transaction atomicity vulnerability, directly conclude that the vulnerability [does not exist]", "6. If the vulnerable function has an onlyowner modifier, directly conclude that the vulnerability [does not exist]" — balanced by "4. When assessing vulnerabilities in functions with permission controls, if the permission roles can be obtained, you still need to consider the vulnerability" and "5. Any vulnerability or risk that could cause potential losses is valid (even small losses)". Useful as *pipeline-level* elimination rules when domain assumptions are known to hold.

### 2.8 "When in doubt, ask for more information" tri-state decision framework
`VulCheckPrompt.vul_check_prompt_agent_initial()` defines the only three valid preliminary outcomes: "✅ Choose \"yes\" ONLY if: The vulnerability clearly exists with current information / ❌ Choose \"no\" ONLY if: You can definitively rule out the vulnerability… / 🔍 Choose \"need_more_info\" if ANY of these apply…" — including incomplete code, unknown callee implementations, external context, or unclear variable usage. Even at the final stage: "if the retrieved information is still insufficient or unclear, you should respond with \"need_more_info\" rather than making an uncertain guess." This tri-state (yes/no/need-more-info) is the engine's core anti-confabulation gate for validators that cannot execute code.

### 2.9 Three-round confirmation with early exit and conservative aggregation
`src/validating/processors/analysis_processor.py` runs up to three confirmation rounds and aggregates: "特殊情况: 第一轮即为 'no' 结果，提前退出验证"; then `yes_count >= 2 → yes`, `no_count >= 2 → no`, and critically "elif no_count >= 1: … final_short_result = 'no'" — any single definitive "no" wins, biasing toward false-negative over false-positive. Failed rounds are recorded as `not_sure` and do not count as evidence.

### 2.10 Verdict taxonomy with explicit judgement criteria (the "judging gate" proper)
`src/validating/finding_checker.py` fixes the machine-readable verdict space: `ALLOWED_VALIDATION_STATUS = {"pending","intended_design","false_positive","vulnerability","vuln_high_cost","vuln_low_impact","not_sure","error"}`. The Codex validation prompt (`src/prompt_factory/validation_codex_prompt.py`) then *defines* each verdict as a falsifiable condition — the single most reusable gate in the repo:

> 「intended_design：行为有文档/注释/显式逻辑支持"这是预期行为"，且不存在可被滥用造成真实损害的路径。 / false_positive：finding 描述/推断与代码事实不符（例如关键条件不存在、权限不可获得、入口不可达、变量不可控、逻辑相反等）。 / vulnerability：存在现实可利用路径，并可能造成明确损害（资金损失/权限提升/资产锁死/DoS 等）。 / vuln_high_cost：漏洞成立但利用门槛很高… / vuln_low_impact：漏洞成立但影响面小… / not_sure：在受控目录内已尽力检索仍不足以确认（必须在 unknowns 中写清楚缺什么）。」

The JSON schema doubles this with independent axes: `exists` (true/false), `classification` (`vulnerability|non_vulnerability|uncertain`), `confidence`, `impact`, `exploit_difficulty` — so a finding can be classified a vulnerability yet rated `hard` to exploit, and export policy can then decide which statuses count.
### 2.11 Evidence-gated agentic verification (search-before-conclude)
The validation prompt forces the judge to gather evidence before verdicts: "你必须先执行多步只读检索（agentic workflow）再给结论：请至少进行 2~5 次检索/交叉引用" (plan version: "至少 3 次，最多 10 次"), including locating the finding's functions, tracing call chains and conditions, verifying "权限、可控输入、外部调用点、状态更新顺序、边界条件", and consulting "README/README_CN、docs/、spec/、design/、whitepaper、audit 相关 md" plus NatSpec before judging intended-design. Outputs must cite `evidence[]` with `file` (relative to workspace root), `locator` (function/variable/line or grep hit), `snippet` ("<= 30 行的关键片段"), and `why`; plus `doc_references[]`, `attack_preconditions[]`, `attack_path`, `mitigation`, and `unknowns[]`. This converts "LLM says yes/no" into "LLM searched, quotes files, and explains which evidence supports which conclusion" — the design doc says the goal is "先在受控目录内检索证据 → 再基于证据给结论", and notes the executed `rg/grep` commands visible in Codex output "非常适合做审计追溯".

### 2.12 Workspace confinement and path-traversal gate
`finding_checker.py` computes the project root strictly from `datasets.json[project_id].path` and enforces `_ensure_under_base()` via `os.path.commonpath`; if the root is missing or escapes the dataset base, *all* findings are marked `error` with the reason rather than letting the judge run anywhere: "无法确定项目根目录：直接将所有 finding 标记 error，避免卡死". Execution uses `CodexSettings` defaults "model: str = \"gpt-5.2\" / sandbox: str = \"read-only\" / ask_for_approval: str = \"never\" / timeout_sec: int = 1800" and the prompt itself forbids out-of-tree assumptions: "你只能读取当前工作目录(workspace root)下的文件来判断，不得引用或假设目录外的任何代码/配置/部署细节。" This is the engine's sandbox/privilege gate for the judge.

### 2.13 Parse-fail-safe verdict downgrade and immutable audit record
`_parse_validation_result()` degrades every malformed output conservatively: empty output → `("not_sure", None, "empty_output")`; no JSON object → `"no_json_object_found"`; parse error → `json_parse_error`; unknown status → `"not_sure", obj, f"invalid_status: {status}"`. Every attempt writes a `validation_record` with `schema_version: validation_codex_v1`, model, sandbox, `workspace_root`, `prompt_hash` (SHA-256 of the prompt, "便于审计与去重"), timestamps, `returncode`, raw `stdout/stderr`, parsed object, and parse error — so no verdict is unreproducible. Non-zero exit, timeout, and Codex CLI errors each map to `validation_status="error"` with the cause recorded.

### 2.14 Export gate: only validated vulnerabilities leave the pipeline
`src/dao/finding_mgr.py` hard-codes the release criteria: export requires `dedup_status != 'delete'` and `validation_status == "vulnerability"`. The refactor plan (docs/VALIDATION_CODEX_REFACTOR_PLAN.md) additionally specifies which statuses should count ("vulnerability / vuln_high_cost / vuln_low_impact" as confirmed vulnerabilities; `not_sure`/`error` "不导出或单独导出到'待人工复核/系统错误'"), plus a legacy mapping (`yes → vulnerability`, `no → false_positive`). Everything below the gate is a candidate; only verified rows become findings.

### 2.15 Task/finding separation with idempotent split and resume state machine
`forward_diff_and_ddl.md` documents the schema refactor that makes multi-vulnerability output tractable: `project_task` keeps the aggregate multi-vulnerability JSON ("供留档/追溯"), while each vulnerability becomes one self-contained `project_finding` row carrying "task 的代码相关字段（name/content/business_flow_code/路径/行号/rule/group 等）". Splitting is idempotent ("幂等方案 A：按 task_id 删除旧 findings 再重建") with `short_result` reduced to a pure split-state (`""/split_done/split_failed`), enabling checkpoint resume: "result 非空且 short_result==split_done → 跳过 / result 非空且 short_result!=split_done → 只补拆分写 finding / result 为空 → 执行扫描 + 拆分写 finding". This "candidates vs. verdicts vs. export" separation is directly portable to any audit pipeline and prevents state pollution between stages.
### 2.16 Business-flow planning with tree-sitter anchor and coverage loop
Planning (`src/planning/planning_processor.py`, `docs/PLANNING_CODEX_REFACTOR_PLAN.md`) forbids hallucinated references: Codex receives a "可用函数清单" built from tree-sitter (`ContractOrLibrary.func` with file path) and every `function_refs` entry "必须严格来自可用函数清单，避免出现外部接口、常量、事件名或裸函数名"; naming rules normalize overloads ("重载函数必须带参数类型签名"), constructors, receive/fallback, and unresolvable interface calls ("接口名.函数名 并在末尾加 (interface)"). A P0/P1/P2 extraction + P3 coverage-repair loop measures covered/uncovered function sets against the catalog and iterates until "覆盖率目标：最终验收 ≥90%"; the docs report "1000行项目，正向抽取覆盖率98%". Tasks are then generated as the Cartesian product "Fi × rule_keys" so each flow is scanned under every checklist dimension. This is a strong *scoping/recon* technique: constrain the planner to a machine-verified function inventory and close the coverage loop numerically.

### 2.17 Fixed invariants and design-doc context injection
`src/reasoning/scanner.py` can inject two types of ground truth into reasoning: `project_design.md` (trust assumptions, hard parameter limits, "EIP violations must be at least medium severity to be valid") and `fixed_invariants.md`, a list of explicit protocol invariants delimited by `<|INVARIANT_SPLIT|>`, e.g. "[EXPLICIT_INVARIANT] Collateral risk score must be constrained by protocol hard upper limits… 0 ≤ collateralFactor ≤ MAX_ALLOWED_RISK… even though governance roles are trusted, the code level must enforce". These act as pre-scoped invariant-hunting targets rather than asking the LLM to invent invariants — a lightweight substitute for formal invariant fuzzing, gated by `ENABLE_DESIGN_DOC_CONTEXT` / `ENABLE_FIXED_INVARIANTS` env flags.

### 2.18 Reasoner / Watcher / Ideator multi-agent loop with budget stop-conditions
`docs/REASONING_MULTI_AGENT_REFACTOR_PLAN.md` + `plan.md` specify a three-role loop per task: **Reasoner** (vulnerability miner; outputs findings + `next_actions` + `stop_signal`), **Watcher** (flow controller with explicit stop conditions: "达到硬预算：max_rounds / max_time / max_no_progress_rounds", "连续 N 轮没有新增高置信 findings", "Reasoner 多次给出相同 next_actions（陷入循环）"), and **Ideator** (divergence engine emitting "可验证的新角度": `new_hypotheses`, `suggested_probes` as `rg` keywords/files/variables, `expected_evidence`, and `coverage_gaps` such as "撤销/退款/暂停/升级/权限变更/边界条件"). The Watcher persists a searchable `memory_store` (by `tag`, `keyword`, `evidence_ref`) with confirmed/rejected/open-question lists to prevent re-mining dead ends. Outputs are split into process-state (per-round traces in `scan_record`) and convergence-state (the multi-vulnerability JSON), keeping the trace machine-replayable.

### 2.19 LLM-driven semantic dedup with "keep-first" and logical delete
`src/res_processor/res_processor.py` deduplicates findings by having an LLM cluster them: "本质相同原则: 只有漏洞的根本原理和成因完全相同才归为一类 / 严格区分原则: 表面相似但本质不同的漏洞必须分为不同类别", outputting `{"group_1":["key1","key2"],...}`; within each group only the first row survives ("多个漏洞，只保留第一个") and duplicates are *logically* deleted (`dedup_status='delete'`) rather than physically removed, so the audit trail is preserved. Validation and export both filter on `dedup_status != 'delete'`.

### 2.20 Context inheritance chains and duplicate-avoidance summaries
Context is inherited across stages by explicit plumbing rather than implicit memory: `CheckUtils.get_code_to_analyze()` prefers `business_flow_code` plus a `business_flow_context` stored in `scan_record`; `ScanUtils.add_dialogue_history_to_prompt()` appends prior findings with the instruction "Excluding these vulnerabilities, please continue searching for other potential vulnerabilities."; `GroupResultSummarizer` compresses results of sibling tasks in the same flow group to reduce re-reporting; and the legacy RAG layer (`AnalysisProcessor.get_available_rag_types`) offers typed context retrieval — name/content/natural-language plus upstream/downstream call-relationship queries — chosen by the LLM itself via `ask_llm_to_choose_rag_for_validation`. The v2 `chunk_config.py` presets (e.g. code: `chunk_size=1000, chunk_overlap=250`, excluding build/dependency patterns) remain as a reference for document chunking, though v3 planning deliberately dropped RAG.

### 2.21 Failure-postmortem culture: distinguish "context missing" from "reasoning failed"
`check_context.md` is a worked example of the engine debugging a false verdict: it re-extracts the functions referenced by a finding's "业务流程代码" and shows the judge had all the code it needed, concluding "这不是上下文不足的问题，而是推理能力不足的问题！" with a concrete mis-inference trace (mis-reading `abort` semantics so a function "returns @0x0" when it actually reverts first). The reusable technique is the *diagnostic protocol*: before adding more context, replay the exact code the judge saw and check whether the claimed facts contradict the visible control flow.

## 3. Contradictions (internal and vs. other methodologies)
1. **Induced hallucination vs. neutral verification.** The project's founding philosophy celebrates hallucination as a recall mechanism — "其核心在于，如何大幅度的触发LLM的幻觉，喜欢幻觉，拥抱幻觉" (philosophy_of_monkey.md) — while the v3 pipeline explicitly removes "诱导式上下文" and requires "Be neutral: vulnerabilities may or may not exist." The two coexist in one repo and are philosophically opposite; most other audit methodologies (and this one's own validation layer) treat hallucination purely as a defect to suppress.

2. **Text-only LLM re-check vs. dynamic execution.** Validation in the shipped code is read-only text retrieval (`sandbox="read-only"`); no contract is compiled, no state transition executed. Yet `plan.md` insists that "Reasoning 与 Validation 在智能合约项目里不仅需要读代码，还需要通过 Foundry 自动生成与运行 PoC 来验证可利用性与影响" and that validation should make "复现与确认" a "第一等公民" by re-running `forge test`. This contradicts toolchains that gate every finding on a passing PoC — here PoC execution is aspirational, and the fallback is explicitly conservative: "若仍无法复现或证据不足，则应保守落为 not_sure".

3. **Blanket rejection rules vs. nuanced verdicts.** The legacy validator auto-rejects reentrancy and any `onlyOwner` function outright ("If the vulnerable function has an onlyowner modifier, directly conclude that the vulnerability [does not exist]"), which contradicts both its own rule 4 ("if the permission roles can be obtained, you still need to consider the vulnerability") and the current Codex taxonomy, where `intended_design` requires that "不存在可被滥用造成真实损害的路径" — i.e., privileged functions are not immune by construction. Blanket rules here are project-specific heuristics, not universal judges.

4. **Export policy divergence.** `ProjectFindingMgr.get_findings_for_export()` exports only `validation_status == "vulnerability"`, while `docs/VALIDATION_CODEX_REFACTOR_PLAN.md` (the design contract) says `vuln_high_cost` and `vuln_low_impact` are also confirmed vulnerabilities and should be exported. Plan/code drift is real and documented ("现有注释是 pending/yes/no/not_sure，后续代码需要同步适配").

5. **Three-round majority vs. single-shot judge.** The old validator aggregates three rounds with "any definitive no wins" (false-negative bias); the new Codex path is a single call per finding (single-point-of-failure for judging, no adversarial second opinion). These represent opposite trade-offs on the precision/recall curve within the same module.

6. **v2 RAG architecture vs. v3 de-scoping.** README still advertises LanceDB RAG, call-tree analysis, and chunking as headline features, while v3.0 updates and all refactor plans explicitly delete them ("removes RAG / chunks / call graph / call tree"; "planning 阶段不再依赖：chunks…call_trees…call_graphs"). Documentation layers contradict the shipped architecture.

7. **Dedup before validation.** The pipeline order in `main.py` is scan → dedup → validation, and dedup keeps only the first finding per cluster. A valid high-impact duplicate variant can be deleted before the judge ever sees it — a lossy gate that other methodologies place *after* confirmation.

## 4. Gaps

- **No deterministic execution or invariant fuzzing harness in the default path.** `fixed_invariants.md` is injected as text, not checked; there is no Echidna/Foundry setup, no fork simulation, and no machine-verified exploit path. Every `exists=true` rests on model reasoning about code, with evidence asserted rather than executed.
- **No severity taxonomy.** The final reasoning schema (`vulnerabilities[].description`) and validation schema carry impact/difficulty but no severity scale (Critical/High/Med…); `project_design.md` references "medium severity" for EIP violations without defining the scale. Cross-finding severity normalization is absent.
- **No automatic verification that cited evidence is real.** The judge is asked to quote file/line, but nothing re-checks that `evidence[].file` exists or that the snippet matches the file content; a hallucinated citation passes the gate.
- **Single-model, single-pass judging.** Validation has no majority vote, no second model, and no disagreement resolution (the old 3-round aggregator was replaced, not merged).
- **No measured false-positive/false-negative rates.** Planning measures *function coverage* (98% on 1k lines), not vulnerability recall; README's "accuracy tracking" is aspirational, and `src/dataset/agent-v1-c4/datasets.json` appears to lack labelled ground truth for verdict scoring.
- **Lossy dedup.** LLM clustering keeps only the first finding per cluster; no merge of evidence from dropped duplicates, and dedup runs before validation.
- **Legacy/new validator coexistence.** Two validation stacks (`ConfirmationProcessor`/`AnalysisProcessor` vs `FindingVulnerabilityChecker`) overlap with inconsistent status vocabularies (`yes/no/not_sure` vs the eight-value enum); the migration mapping is described but not implemented.
- **Judge sandbox hygiene.** `read-only` sandbox still permits reading sibling findings/logs in some configurations; nothing defends against the model treating `scan_record` contents as ground truth (context contamination).
- **Prompt-versioned records are advisory.** `schema_version: validation_codex_v1` is written by the caller, not enforced end-to-end; old rows lack the version.

## 5. Classification in the Unified Security Skill Taxonomy

- **Core methodology** — the Planning → Reasoning → Validation pipeline, taint-template × question-direction framework, business-flow task decomposition, and finding-level data model form a complete, reusable audit workflow rather than a single technique.
- **Validation mechanism** — the eight-value verdict taxonomy with falsifiable judgement criteria, evidence/document requirements, parse-fail-safe downgrade, idempotent split, logical-delete dedup, and export gating are directly extractable validation machinery.
- **Judge mechanism** — the Codex read-only agentic judge ("search before concluding", 3–10 retrievals, JSON-only verdicts with evidence arrays, workspace confinement) is a concrete instantiation of an LLM judge with auditable traces.
- **Tool integration** — Codex CLI orchestration (`sandbox`/`ask_for_approval`/`timeout` settings), tree-sitter parsing, PostgreSQL persistence (`project_task`/`project_finding` DDL), and optional Foundry PoC re-run define an integration pattern for wrapping an agentic CLI in a controlled audit harness.
- **Reference material** — the refactor plans (`VALIDATION_CODEX_REFACTOR_PLAN.md`, `REASONING_MULTI_AGENT_REFACTOR_PLAN.md`, `PLANNING_CODEX_REFACTOR_PLAN.md`, coverage-repair plan), `Methdology_approach.md`, `fixed_invariants.md`, `project_design.md`, and the `VulPromptCommon` checklist library are high-quality prompt/checklist reference assets reusable outside the engine.
